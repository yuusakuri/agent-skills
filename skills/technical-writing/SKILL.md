# 技術文書の執筆

## 作業の流れ

1. 編集前に、読者、読者が行う作業、文書の種類を特定する。利用者から十分な情報が得られている場合は、最も合う種類を選んで進める。
2. 草稿の作成や再構成では、`references/document-types.md` から構成を選び、`assets/templates/` から対応するテンプレートを選ぶ。
3. `references/structure-principles.md` の情報構成の原則を適用する。1ページ1話題、価値を先に示すこと、効果的な見出し、概要、予測しやすい順序、十分な背景説明を扱う。
4. `references/sentence-style.md` に従って文章を推敲する。明確な主語、能動態、簡潔さ、具体性、自然な表現、用語の一貫性を確認する。
5. `references/review-rubric.md` でレビューする。利用者がレビューを求めた場合は、大幅に書き換える前に指摘事項を報告する。

## 作業別の参照先

- 文書全体の執筆・書き直し：`document-types.md` を読み、テンプレートを1つ選び、利用者から得た情報で仮置きの項目を埋めながら直接執筆する。
- 既存の草稿のレビュー：`review-rubric.md` を読み、重大度順の指摘事項、具体的な修正方法、短い要約を返す。
- メモや粗い草稿の再構成：`structure-principles.md` を読み、先に章立てを作る。本文の書き直しは依頼された場合に行う。
- 文章の推敲：`sentence-style.md` を読み、元の意味と技術的な記述を維持する。
- プロンプトやAIを使った執筆手順の作成：`prompt-workflows.md` を読み、執筆、構成、レビューに再利用できるプロンプトを作る。
- 出典とライセンスの適用範囲の確認：`source-map.md` を読む。

## 保持する事項

- 利用者から明示的な変更依頼がない限り、コードブロック、コマンド、API識別子、パラメーター名、バージョン番号、警告、エラーメッセージ、日付、測定値、製品の動作を保持する。
- 不明な技術的事実を作らない。不足箇所は質問またはTODOとして示す。
- 曖昧な利点より、具体例、条件、前提、期待する結果を示す。
- 見出しは予測しやすく、検索に必要な語を含むものにする。検索しやすさが必要な場面で、凝った見出しを使わない。
- 実装の詳細より先に、読者にとっての価値や得られる結果を示す。
- 韓国語の草稿には、`sentence-style.md` の韓国語の自然さに関する注意事項を適用する。英語の草稿では、自然な英語表現を維持し、逐語訳調を避ける。

## 出力の既定形式

- レビュー：指摘事項を先に示し、重大度順に並べる。可能であればファイルや節の位置を示す。
- 草稿：章立てだけを求められた場合を除き、完成した草稿を返す。
- 章立て：想定読者、文書の種類、節の一覧、関連文書へのリンク案を含める。
- 書き直し：保持した制約と、未解決の事実の不足箇所を伝える。
